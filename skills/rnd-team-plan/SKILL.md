# 多人实施计划

读取当前规格、验收、代码结构、现行团队分工和必要专项决定。负责可执行任务、接口依赖、分工建议及检查安排；由当前计划维护人整合权威计划。

## 分批与实验安排

按可验收结果及依赖分批，区分任务分工、人工检查点和会话边界。规模依据实际未知项、影响、恢复成本、验证依赖和分批交付需要判断；多文件/多函数不单独触发检查点。明确、局部可逆且可一批验证的迁移/重构，在现有任务授权内直接接续，无需额外连续执行声明。确需分批可靠交付或有多项重要取舍的较大任务，首次既无批次约定、也无明确连续执行偏好时先交具体建议，依共同约定取得有权决定者答复。已有停止点优先。计划标明谁有权确认相关范围/接口及何时需要确认，不默认集成者可扩大范围。

调研计划组织方法、数据/样本、对照、覆盖与执行安排；脚本/配置/输出交实际执行维护人。方法问题留本角色，分析问题交分析维护人及 discover，不强行安排产品开发。修订后的受影响检查对应当前方法版本，保留原失败证据。

## 本次范围与证据

明确且低风险的受托任务无需为了进入 build 补造计划或验收编号；已有适用计划仍遵循。先读现有依据，只澄清实质未知项；信息充分即返回实施。调查消除复杂性时，现行维护人在原处缩减未执行安排，保留决定、依赖和检查，其他成员交建议而不覆盖共享计划。

关键反例探针先于依赖实现、推广及大量重复稳定性测试，保留既定次数门槛。拒绝/隐藏安排触发、解除与同实例恢复检查，按需覆盖模态取消、单例/多例。原生桌面涉及普通、铺满、原生全屏、小窗口及适用多屏时，交 design 按其原生桌面参考检查用户任务能否完成；真实渲染与几何推断分开。

RED 分类记录：新接口缺类型/函数的编译失败可证明接口尚不存在；旧缺陷须有行为失败或最小真实复现与修后同测，数量不能代替覆盖。计划引用验收，只写实施、依赖和证明安排，不复写完整行为参数。

## 方法

1. 沿用已有任务/Issue，在 [协作记录](references/workflow.md) 中明确任务 ID、实际负责人、验收 ID/规格依据、文件或模块范围、独立分支/工作树、前置依赖、接口与检查。没有人员分配依据时写“待分配/建议”，不能虚构已认领。协调及集成负责人引用现行分工。
2. 按可独立交付的行为拆分任务。不同成员共同改同一文件/章节时注明串行整合者与顺序；共享接口、数据库迁移、公共配置/依赖由明确维护人统一处理，不把互相覆盖的任务标为可安全并行。
3. 新增行为安排失败断言 → 确认因缺行为而失败 → 最小实现 → 相关检查通过。低影响文字修改直接核对。选择项目真实 scripts/CI，说明 cwd、验证行为、输入和预期结果，将验收对应到任务及证明方式。
4. 明确接口现行合同与未确认点、兼容安排、受影响任务和集成顺序。成员交接带准确版本/完整未提交交接包、证据、接收人及剩余项；安排集成版本上的真实模块交互与受影响回归，成员单测通过不等于整体验收。
5. 核对任务范围、依赖及验收覆盖，注明项目必需的审查与授权。已有文档或一张任务表足够就沿用；规格问题交实际规格维护人，不另起规格或编排系统。

## 核验与返回

计划明确后交对应任务负责人；缺分工或共享合同只阻塞依赖它的工作。计划/接口安排缺陷按 RTN-2 交实际维护人修复，合并核验由指定集成者协调。

方法来源见 [固定方法](references/methods.md)。沿用 Superpowers 的具体文件、依赖、RED/GREEN；多人任务字段、分工和集成约定为集合综合适配。
