# 逐项完成核验

读取当前验收、实现、检查输出、审查和适用发布事实。负责给出有证据的完成结论。

## 多人任务边界

先明确核验的是成员任务还是整体集成结果，注明准确版本/完整未提交交接包、负责人与当前验收依据。整体结论补真实模块交互与受影响回归；各分支绿色不能相加成合并后的绿色，未执行的集成检查保留未验证。

[接手、分工与交接字段](references/workflow.md) 使用项目现有记录；只有本地草稿时不声称已通知或同步给其他成员。

## 按目标确定证明

文档交付核对对应质量及请求范围；调研区分执行完成、证据覆盖、目标/假设是否成立与分析是否相符，负面结果不等于未做研究。只审查请求可完成发现交付，开放问题不等于产品已通过。项目技术类型决定实际证明：例如接口看真实交互，数据任务看输入与转换结果，界面看渲染/操作，实验看样本和方法；需要的领域核验沿用项目工具。

## 本次范围与证据

明确且低风险的请求没有正式验收编号时，直接逐请求要求及相关现有事实核对，不补造规格或 AC ID；已有适用计划、用户指定文档及项目要求仍有效。核验只记录依据引用、证据、结论和缺口，不复写完整行为参数。

人工结果按协作约定绑定实际运行候选与轮次，分列源码、新构建、成员/集成候选及运行实例；简短成功仅覆盖该轮的应用、样本、模式与动作。拒绝/隐藏核对触发、解除及同实例合法恢复，重启不替代原地恢复。编译 RED 可证明新接口尚不存在，不证明捕获旧缺陷；旧缺陷检查行为失败/真实复现和修后同测，数量不能替代覆盖。

## 方法

1. 先明确每项完成声明需要什么证明，再逐已有验收 ID 或明确请求要求对照真实行为、覆盖范围、当前版本和未关闭问题。
2. 阅读实际执行的命令、cwd、退出码和完整输出，必要时只补受影响的检查。不能拼接不同尝试充当一次通过，也不能在新失败之后引用旧成功充当现行结果。
3. 区分研发完成、发布就绪和上线验证。研发看当前行为与必要检查/审查；发布还看候选版本、目标环境、授权与恢复准备；上线还看真实部署及约定观测。
4. 未运行、缺项、中断、未知环境分别说明，不能提升为通过。自审不称独立，模拟不称真实上线。
5. 将验收项、证据位置、核验结果和缺口记录到项目现有文档或任务章节。已有证据内容、环境及相关输入没变时可引用复用，受影响部分重新核对。

## 交付

向用户说明具体实现并验证了什么、还缺什么。纯技能版的结论来自 Agent 对实际证据的核验，没有集合自动门禁或身份认证保证；若项目自带门禁，同时保留它的原始结论。

失败依 [责任映射](references/workflow.md) 返回作者，未知归属先调查。保留 Superpowers 先确定证明、执行、读完整输出再下结论的方法，见 [固定来源](references/methods.md)。
