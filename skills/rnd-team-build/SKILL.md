# 实现与根因修复

读取当前要求、相关代码、已有适用计划/规格/验收和专项；已有计划按计划实施，明确且低风险的受托任务可直接依据请求及现有事实实施，不因缺计划阻断或补造计划。负责代码、测试与真实执行证据；在用户已授权范围持续执行。

## 多人任务边界

先核对本人任务、实际负责人、允许修改范围、当前共享合同及独立工作目录。实现记录与交接必须带任务 ID、准确版本或符合协作约定的完整未提交交接包、真实检查、接收人和剩余项；成员结果交审查/集成，不自行提升为整个功能完成。发现接口或范围变化时交当前维护人处理，继续不受影响的工作。

[接手、分工与交接字段](references/workflow.md) 使用项目现有记录；只有本地草稿时不声称已通知或同步给其他成员。

## 接续与研究执行

本人完整任务内，实施/修复后交回 lead 继续适用 review/verify；四项返回为产物、实际结果、未解决项、下一动作。到约定检查点停下报告准确版本；待答不实施，部分确认只实施子集。公共合同或他人制品变化交其维护人，继续明确且不受影响部分。

调研实现实验脚本、配置和执行事实；按已确认方法/指标执行，区分进程成功与目标达成，不改数据或阈值迎合结论。方法/覆盖问题交方法维护人及 plan，分析问题交分析维护人及 discover。本人修复保留原输出并补受影响检查。

## 本次范围与证据

关键反例探针先于依赖实施。区分新接口缺类型/函数的编译 RED 与捕获旧缺陷的行为 RED；旧缺陷尽可能在旧实现取得行为失败，再对修复版同测。外部系统保留最小真实复现，不能自动化的部分注明真机复验缺口；测试数量不证明覆盖。

准备人工验收按协作约定绑定实际运行候选、应用、样本、窗口模式及动作，分列源码、新构建和运行实例。待答候选可能被覆盖时，由有权维护它的人保存并核对可恢复产物；不擅自替换其他成员正在验收的实例。短答成功不能移用到新候选。

## 方法

1. 按依赖顺序实施。新增行为先写失败断言，运行并确认失败原因，再最小实现并确认通过；测试实际行为，避免只复述实现或验证 mock。
2. 调试按四阶段进行：复现与根因定位 → 对照有效例找差异 → 单一假设做最小试验 → 用失败回归和修复验证。多次修复无效时重新检查假设和架构。
3. 使用项目现有测试、构建和检查命令，保留真实 cwd、命令、退出码和输出。相关检查通过后核对必要门禁，已有充分证明时停止重复测试。
4. 实现与计划接口不符时记录偏差并交 plan；验收不可判定交 spec。保持修改范围，不重构无关部分，不代改验收消除失败。

## 核验与返回

交付具体修改、检查结果、未解决项和偏差，再交 reviewer。非零退出保留为失败，中断和缺项如实说明；实施缺陷或计划内测试遗漏由本角色修复（RTN-3）。

参照 [协作约定](references/workflow.md)；改编 Superpowers 执行、TDD 和 systematic-debugging，见 [固定来源](references/methods.md)。
